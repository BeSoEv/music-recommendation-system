# Рекомендательная система для музыкального сервиса

## 1. Описание проекта

Проект посвящён разработке рекомендательной системы для музыкального сервиса.

**Задача:** по истории событий пользователя предсказать, какие треки он будет слушать в дальнейшем.

Для каждого пользователя необходимо сформировать до 10 рекомендаций, упорядоченных от наиболее релевантной к наименее релевантной.

Особенности задачи:
- Используются реальные логи музыкального сервиса: прослушивания, лайки и дизлайки.
- Каталог содержит более 880 тысяч треков.
- Повторные прослушивания разрешены и считаются попаданиями.
- Оценка качества производится по метрике NDCG@10.

## 2. Данные

В основе данных лежит датасет Yambda-50M от Яндекса (лицензия Apache-2.0). Идентификаторы пользователей и треков переиндексированы, временные метки сдвинуты на постоянную величину.

Используются следующие файлы:

| Файл | Описание |
|---|---|
| `train.parquet` | Обучающая выборка, содержащая около 43 млн событий |
| `test_users.csv` | 9213 пользователей, для которых необходимо сформировать рекомендации |
| `sample_submission.csv` | Пример файла с рекомендациями |

### Основные признаки `train.parquet`

| Признак | Описание |
|---|---|
| `uid` | Идентификатор пользователя |
| `timestamp` | Время события в секундах |
| `item_id` | Идентификатор трека |
| `is_organic` | Признак органического прослушивания |
| `played_ratio_pct` | Доля прослушанного трека в процентах |
| `track_length_seconds` | Длительность трека в секундах |
| `event_type` | Тип события: listen, like, unlike, dislike, undislike |

### Особенности данных

- Временное разделение выполнено по 90-му процентилю времени прослушиваний.
- Обучающая выборка содержит события до временной границы.
- Целевые события — прослушивания после временной границы.
- 151 тестовый пользователь отсутствует в обучающей выборке и требует отдельной обработки.

Исходный датасет Yambda не используется для обучения или сопоставления идентификаторов.

## 3. Метрика качества

Метрика — NDCG@10, усреднённая по пользователям. Каждое попадание в топ-10 приносит тем больше, чем выше стоит трек, а результат нормируется на лучший возможный для этого пользователя.

## 4. Архитектура решения

Решение реализовано в виде двухэтапной рекомендательной системы:

1. Генерация кандидатов.
2. Ранжирование кандидатов.

### 4.1. Генерация кандидатов

Используются три независимых источника рекомендаций.

#### iALS

Применяется модель Implicit Alternating Least Squares для работы с неявной обратной связью.

В качестве входных данных используется матрица взаимодействий пользователей и треков, построенная по событиям прослушивания.

Выбранные параметры:
- `factors = 128`
- `alpha = 10`
- `regularization = 0.01`
- `iterations = 20`

#### BPR

Применяется Bayesian Personalized Ranking — модель парного обучения для персонализированного ранжирования.

Для обучения используется бинарная матрица взаимодействий: учитывается факт прослушивания трека, а не количество прослушиваний.

Выбранные параметры:
- `factors = 128`
- `learning_rate = 0.05`
- `regularization = 0.01`
- `iterations = 30`

#### Кандидаты на основе истории прослушиваний

Дополнительно формируется список треков из истории каждого пользователя.

Для каждой пары пользователь-трек рассчитываются:
- количество прослушиваний
- давность последнего прослушивания
- сумма экспоненциально взвешенных прослушиваний за 7 дней
- сумма экспоненциально взвешенных прослушиваний за 30 дней

Для учёта актуальности предпочтений используются экспоненциальные веса

Внутри истории каждого пользователя треки ранжируются по трём критериям:
- взвешенная активность за 7 дней — топ-300
- взвешенная активность за 30 дней — топ-150
- общее количество прослушиваний — топ-100

В итоговый кандидатный список включаются треки, попавшие хотя бы в один из этих списков.

### 4.2. Объединение кандидатов

Кандидатные списки iALS, BPR и истории прослушиваний объединяются.

Повторяющиеся пары пользователь-трек удаляются

Таким образом, формируется единый пул кандидатов, для которых рассчитываются признаки

### 4.3. Ранжирование

Для ранжирования используется `CatBoostRanker` с функцией потерь `YetiRank`.

Модель обучается на признаках, характеризующих взаимодействие пользователя с треком и результаты работы моделей генерации кандидатов.


**Признаки iALS и BPR:**
- оценки моделей
- ранги треков
- индикаторы присутствия трека в кандидатных списках моделей

**Признаки истории прослушиваний:**
- количество прослушиваний
- давность последнего прослушивания
- взвешенная активность за 7 и 30 дней
- ранги треков по соответствующим показателям

**Дополнительные признаки:**
- популярность трека
- размер истории пользователя

Популярность трека определяется количеством его прослушиваний в обучающей выборке. Размер истории пользователя определяется количеством уникальных прослушанных им треков.

## 5. Обучение и формирование рекомендаций

После выбора параметров и проверки качества моделей выполняется повторное обучение iALS и BPR на полной обучающей выборке.

Далее для тестовых пользователей:
1. Получаются рекомендации iALS и BPR
2. Формируются кандидаты на основе полной истории прослушиваний
3. Объединяются все кандидатные списки
4. Рассчитываются признаки для каждого кандидата
5. CatBoostRanker предсказывает оценки релевантности
6. Для каждого пользователя выбираются 10 треков с наибольшими оценками

Для пользователей без истории рекомендуем топ 10 популярных треков обучающей выборки
